# Working through slide comments

He sends comments from the deck, often a dozen in a few minutes, and reads the replies in each thread.

## For each comment
1. **Re-read the live slide** before changing it; it may have changed since you last saw it (his own edits included).
2. **Read the comment as a request about that spot.** Short comments are complete instructions:
   - "delete" → delete that element (and anything that only existed for it).
   - "bigger font" / "bigger circle" → clearly bigger (+20–40%), then re-check the layout.
   - "what is X?" / "i don't understand this" → the slide is unclear: answer in the thread **and** rewrite the slide.
   - "you mean …?" → he is proposing wording; usually adopt it.
   - "is this because of …?" → answer with the source; add the answer to the speaker notes, and offer a slide line.
   - "maybe i am wrong" → check the source honestly; say plainly if he is right.
3. **Make the change.** Small text edits: an in-place edit of that one file. Structural changes or several slides: rebuild locally, preview, publish together.
4. **Keep your local copy in sync** after every in-place edit, or a later publish will undo it.
5. **Preview**: no overflow, sources at the bottom.
6. **Reply in that comment's thread**: quote the new wording or describe the new visual; give numbers and sources when you looked something up. Don't resolve the thread.
7. **One short line in chat**: what changed and that the reply is in the thread.

## When many arrive at once
Handle them all, batch the edits into one publish, and reply in every thread. If a comment was already handled by an earlier change, say so in one line and don't redo it. When a later comment contradicts an earlier change (e.g. "delete this slide" after you rebuilt it), follow the later one and offer to restore.

## Learn from them
A comment that states a general preference ("reference should always be bottom") applies to the whole deck: fix every slide, not just the one commented on. Offer to add new preferences to `rules.md`.
